# Authenticated Atlassian Customer Service Management widget

Planyx uses two Atlassian Customer Service Management widgets:

- Public and signed-out visitors: `2e5cd7dc-e84b-41b5-a6c8-805909741566`
- Signed-in Planyx customers: `7e246b9d-dc9b-46e1-b41b-2997edbfe4da`

The browser selects the widget only after the Planyx customer authentication state has finished loading. The signed-in widget calls the same-origin endpoint `POST /csm-widget-token` whenever Atlassian needs an access token.

## Required Cloudflare secrets

Configure the following values in the production Cloudflare environment:

- `CSM_WIDGET_CLIENT_ID`
- `CSM_WIDGET_CLIENT_SECRET`

These are the Client ID and Client secret generated by Atlassian for the personalised widget. They are not the widget ID or cloud ID.

The values must remain server-side Cloudflare secrets. Do not add them to source control, public environment variables, browser JavaScript, build output or screenshots.

The endpoint also depends on the existing Planyx customer OIDC configuration and D1 binding used by `getNativeSession`.

## Token flow

1. The visitor signs in through JA Group Services ID.
2. Planyx validates the existing `ja_customer_oidc_session` HTTP-only cookie against the customer OIDC session table.
3. The server reads the verified email from the validated session.
4. The server creates a 60-second HS256 JWT assertion containing `sub`, `iss`, `iat` and `exp`.
5. The assertion is exchanged at `https://auth.atlassian.com/oauth/token` using the JWT bearer grant and the `csm:atlassian-internal` scope.
6. Only the returned `access_token` is sent to the widget.

The endpoint does not accept an email address from the request body, query string or browser-provided identity headers.

## Security behaviour

- POST only
- Same-origin requests only
- Valid signed-in customer session required
- Customer realm only; Admin sessions do not qualify
- No caching; responses use `Cache-Control: no-store`
- The token endpoint is disallowed in `robots.txt`
- Client secrets and JWT assertions are never returned to the browser or written to normal logs

## Expected responses

- `200` with `{ "access_token": "..." }` for a valid signed-in customer
- `401` when there is no valid customer session
- `403` for an invalid request origin
- `501` when the Atlassian widget credentials have not been configured
- `502` when Atlassian rejects or fails the token exchange
